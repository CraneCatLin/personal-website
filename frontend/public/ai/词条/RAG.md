# 检索增强生成  
  
## 核心摘要  
  
RAG 通过检索外部知识库中的相关文本块，将其作为上下文附加到用户查询中，由大语言模型生成最终答案。底层实现包括：文本向量化（嵌入）、近似最近邻索引（HNSW、IVF）、文档分块策略、重排序模型（Cross-Encoder）以及基于模板的提示词构造。关键技术指标为检索延迟 O(log N)（HNSW）和生成质量受召回率影响。  
  
## 关键信息提炼  
  
### 1. 向量嵌入  
  
- 编码模型（Sentence-BERT、OpenAI `text-embedding-3-small`）将文本映射到高维空间（维度 d = 768, 1536）。  
- 训练方式：对比学习，最小化语义相似样本间的余弦距离，最大化不相似样本的距离。  
- 输出归一化：L2 归一化使向量模长为 1，余弦相似度等价于点积：  
  $\text{sim}(A,B) = A \cdot B = \sum_{i=1}^{d} A_i B_i$  
  其中 $||A||=||B||=1$。  
- 池化操作：最后一层 Transformer 输出经 Mean Pooling 或 CLS Pooling 得到固定长度向量。  
  
### 2. 向量检索与近似最近邻  
  
- **精确检索**：暴力计算所有点积，时间复杂度 O(N·d)，不可用于大规模数据。  
- **HNSW（Hierarchical Navigable Small World）**：多层图结构，上层节点稀疏（高速路），下层全连接。检索时从顶层贪心下降，每层局部搜索邻居。时间复杂度 O(log N)，空间复杂度 O(N·log N)。  
- **IVF（Inverted File Index）**：K-means 将向量空间划分为 nlist 个 Voronoi 单元。检索时计算目标点与各聚类中心距离，只搜索最近的 nprobe 个单元内的向量。复杂度 O(nprobe · (N/nlist) · d)。  
- **向量数据库示例**：FAISS 的 `IndexHNSWFlat`，构建参数 M（每个节点最大边数）、efConstruction（动态候选列表大小）。  
  
### 3. 文档分块  
  
- **固定大小分块**：按 token 数切分（如 512 token），重叠窗口（10%）避免语义截断。实现使用滑动窗口：`[i*step : i*step+chunk_size]`。  
- **语义分块**：基于句子嵌入向量的相似度。计算相邻句子向量的余弦相似度，低于阈值时切分。  
- **递归分块**：按分隔符优先级 `["\n\n", "\n", " ", ""]` 递归尝试切分，使块大小不超过上限。  
  
### 4. 重排序  
  
- **Cross-Encoder 模型**（如 `BAAI/bge-reranker-base`）：输入为 `[CLS] query [SEP] document [SEP]`，输出 0~1 相关性分数。  
- 与双编码器区别：双编码器可预计算文档向量，Cross-Encoder 必须实时计算每对 `(query, doc)`，因此计算量 O(k·d_model²)（k 为候选数），但准确率更高。  
- 流程：检索器返回 k（如 20）个候选 → 对每个候选执行 Cross-Encoder 前向传播 → 按新分数取前 n（如 5）个送入生成模型。  
  
### 5. 增强与生成  
  
- **提示词模板**：  
  ```  
  根据以下信息回答问题：  
  {context}  
  问题：{question}  
  回答：  
  ```  
- **上下文截断**：若总 token 数超过 LLM 窗口上限，按保留策略截断：  
  - 按检索分数降序保留。  
  - FIFO（先进先出）丢弃最早块。  
- **解码**：LLM 自回归生成，注意力机制同时处理问题与上下文。提供真实信息可降低幻觉概率。  
  
### 6. 常见优化  
  
- **HyDE**：先由 LLM 生成假设答案，再用假设答案向量检索。原理：将查询向量映射到文档向量空间，提高召回率。  
- **混合检索**：向量检索（语义）与 BM25（关键词）结合，使用 RRF（倒数排名融合）：  
  $\text{RRF}(doc) = \sum_{i=1}^{m} \frac{1}{k + r_i(doc)}$  
  其中 $r_i(doc)$ 是 doc 在第 i 个检索结果中的排名，k 为常数（通常 60）。  
- **多向量检索**：每文档块生成多个向量（实体向量、摘要向量），检索时合并投票。  
  
## 专业延伸  
  
**索引构建与查询的时间复杂度权衡**：HNSW 的构建时间为 O(N·log N·M)，内存占用约为原始向量的 2~3 倍（因存储图边）。IVF 构建时间为 O(N·d·nlist)（K-means 迭代），内存更低，但查询精度低于 HNSW。实际系统中常采用 HNSW 作为默认索引，仅当内存受限时使用 IVF。
